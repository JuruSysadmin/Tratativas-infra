# Split Chat Room Responsibilities Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Replace `ChatWeb.ChatRooms` with focused LiveView helper modules while preserving its public behavior, security checks, and the `{:ok, socket}` / `{:error, reason, socket}` room-mutation contract.

**Architecture:** Keep `Chat.Rooms` as the domain context and move only LiveView socket orchestration into four stateless modules under `ChatWeb`. `ChatWeb.ChatState` remains the owner of message loading, presence, and notification orchestration; focused modules may call its existing public functions where the current contract requires selecting or clearing a room.

**Tech Stack:** Elixir, Phoenix LiveView, Ecto, Phoenix PubSub, ExUnit.

---

## Current context

`lib/chat_web/live/chat_rooms.ex` currently combines four independent responsibilities:

- UI room state and explorer/dialog navigation: `init/1`, `refresh/1`, `open_new_room_dialog/1`, `open_room_explorer/1`, `close_dialog/1`, `search/2`, `clear_search/1`, `find_assigned_room/2`.
- LiveView room lifecycle actions: `create/3`, `join/3`, `leave/3`, `confirm_delete/3`, `delete/3`.
- Unread badge persistence/synchronization: `increment_unread/2`, `clear_unread/2`, `refresh_unread/2`.
- PubSub subscription management: `subscribe/2`, `unsubscribe/2`, private bulk subscription helper.

`ChatWeb.ChatLive` and `ChatWeb.ChatState` are the only production callers. `test/chat_web/live/chat_rooms_test.exs` is the focused regression suite and should be split along the same responsibility boundaries.

## Public-module boundaries

### `ChatWeb.RoomNavigation`

Owns socket assigns that represent room navigation and explorer UI:

- `init/1`: loads user rooms, delegates unread initialization to `UnreadTracking`, initializes dialog/navigation assigns, and delegates room-topic subscriptions to `PubSubManager`.
- `refresh/1`: reloads rooms and calls `UnreadTracking.reload/2` using the refreshed list.
- `open_new_dialog/1`
- `open_explorer/1`
- `close_dialog/1`
- `search_available/2`
- `clear_search/1`
- `find_assigned_room/2`

`RoomNavigation` is intentionally the single owner of `:rooms`, `:room_dialog`, `:available_rooms`, `:room_search`, and `:navigation_open` initial assignments.

### `ChatWeb.UnreadTracking`

Owns only the `:unread_counts` assign and always derives it from persisted membership/message data:

- `initialize/2` accepts `socket` and the already-loaded room list.
- `reload/2` accepts `socket` and the refreshed room list.
- `increment/2`, `clear/2`, and `refresh/2` preserve the current semantics: no in-memory arithmetic; query `Messages.unread_counts_by_room/2`.

The two collection functions prevent a duplicate `Enum.map(rooms, & &1.id)` implementation.

### `ChatWeb.PubSubManager`

Owns room-topic subscription mechanics and the authorization guard:

- `subscribe/2` only subscribes a connected socket when `Rooms.room_member?/2` confirms membership.
- `unsubscribe/2`
- `subscribe_rooms/2`

Keep topic construction private in this module. No other new module should build `"room:<id>"` strings.

### `ChatWeb.RoomManagement`

Owns the CRUD/action contract exposed to LiveView event handlers:

- `create/3`, `join/3`, `leave/3`, `confirm_delete/3`, `delete/3`.
- Success remains `{:ok, socket}`; errors remain `{:error, reason, socket}` except `confirm_delete/3`, which keeps its existing `{:ok, room}` / `{:error, :not_authorized}` confirmation contract.
- It composes `RoomNavigation.refresh/1`, `PubSubManager.subscribe/2` or `unsubscribe/2`, `ChatState.select_room/2` or `clear_selected_room/2`, and `ChatState.refresh_mentions/1` exactly as `ChatRooms` does now.

The direct dependency from `RoomManagement` to `ChatState` preserves existing behavior and avoids changing event-handler contracts during this extraction. A later, separate refactor could remove that dependency by moving full room selection orchestration from `ChatState` into `RoomNavigation`; do not combine that larger redesign with this split.

## Risks and trade-offs

- `ChatState` currently depends on `ChatRooms`, and room mutations currently call `ChatState`. Replacing all behavior in one change risks an accidental lifecycle ordering change. The compatibility bridge and sequential migration preserve behavior.
- The names requested are `ChatWeb.*`, but these modules are not Phoenix/Ecto contexts; they are stateless LiveView orchestration modules. Keeping them under `ChatWeb` is appropriate because they operate on LiveView sockets.
- `RoomManagement` must not bypass `PubSubManager.subscribe/2`; its membership check is a security boundary validated by the IDOR regression test.
- Room membership is checked in the domain context (`Chat.Rooms`). Do not duplicate CRUD rules in `ChatWeb.RoomManagement`.
- Do not add processes, behaviours, or new dependencies; this is an extraction of pure functions around an existing socket state flow.
- User preference forbids commits unless explicitly requested, so omit the commit steps suggested by generic planning conventions.
